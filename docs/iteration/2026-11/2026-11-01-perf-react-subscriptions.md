# 输入与运行态刷新性能

日期：2026-11-01。开发状态以 [roadmap](../../roadmap.md) 为准。

## 目标与范围

解决 250 条历史会话时逐字输入引发的侧栏整树刷新，并减少流式输出、Host UI 和输入工具栏的无关订阅。保持 G1.3 行为、协议和多窗口语义；涉及 SES-02、RUN-01/06、MOD-01、输入与 Host UI 的既有能力。

基线使用独立测试宿主和 250 条合成历史：开发模式按键往返中位数约 151ms、P95 200ms，每字出现长任务；过滤为空约 34ms。保留列表而稳定侧栏字段的诊断实验约 34ms，无长任务。原始本地产物位于 `apps/harness/test-results/perf-review`；往返含自动化协议与双帧等待，测量口径与 INP 不同。

## 设计

1. 侧栏仅订阅必要的远端 ID/标题字段，字段未变时复用选择结果；保持宿主元数据权威，保留 initialize 本地 ID 到 remoteId 的映射。memo 行传入稳定数据和自身活动态，弹层按需挂载，减少所有行同时执行。
2. runtime actions 按 Controller 生命周期稳定；消费方按字段或稳定 actions 订阅，完整 extras 仍供需要完整状态的调用方使用。长期连接依赖 Controller。Host UI 游离请求只在请求数组变化时分组；widget 先订阅原数组再派生。
3. 关闭的会话树不订阅输入文字；执行动作时读最新草稿。Composer 工具栏/模型区与高频文字更新隔离，历史维护不随每段 assistant 输出全表扫描。Workspace Context 按动作和数据分别订阅，避免为本次引入额外权威或全量 store 迁移。
4. 使用现有 React/selector/Zustand 能力，不新增依赖。本轮暂以消除无关刷新为验收；虚拟化和长消息投影算法根据后续实测单独决定。

## 验证

- 补有行为意义的稳定动作/请求订阅与大列表输入、流式回归，确认切换 Controller 后动作绑定正确。
- 250 和 1,000 条合成历史测输入与流式输出，无关会话行不执行；相同机器开发模式 250 条输入往返建议中位数 ≤50ms、P95 ≤75ms，20 字无长任务。区分 StrictMode 调用、提交与 DOM 更新。
- 对照生产构建测量，记录实际结果，不将开发双帧值称纯输入延迟。
- `pnpm check`、`pnpm build`、完整 Chromium 回归；保留新建/远端 ID、工作区、归档删除、树导航、多窗口、断流、队列、附件/IME、Host UI 领取和焦点检查。
- 主 agent 独立审阅与亲验。所有性能数据来自隔离临时空间与合成模型。

## 风险与回退

字段比较不得遗漏 UI 使用的标题、运行态、活动态或 ID 映射；memo 不得捕获过期动作。按需弹层保留关闭/焦点行为；动作读取草稿须在调用前固定必要内容。连接保持原有引用计数和延迟释放。保留既有 G1.3 未提交内容；需要回退时仅撤销本迭代修改，不整库还原。

## 执行与验证记录

- subagent 完成主体实施；主 agent 独立审阅、直接修复并运行验证。模型预检为 `opencode-go/deepseek-v4.1-flash:max`。
- 侧栏字段投影使用公开 `useAuiState`，按字段比较而非 JSON 序列化；保留 localId/remoteId 映射。会话行按自身活动态及实际显示/弹层字段比较，避免目录刷新新对象扩散；三种弹层打开时挂载，关闭焦点回归有浏览器断言。
- `HarnessRuntimeActions`/`useHarnessActions` 按 Controller 保持稳定，切换 Controller 重绑；Host UI 分组引用按请求数组缓存；长期连接依赖 Controller。工作区拆数据/动作 Context，refresh 从最近接受的响应读取引用，保留刷新代次守卫。
- 关闭的树面板不订阅文字，模型区及相关按钮使用稳定 props。输入历史从 Controller 权威消息建立加载基线，新增用户消息才扫描；首条创建从占位 Controller 切换时保留本窗口提交。主 agent 通过原有首条历史和新增旧会话历史回归修正加载时序问题。
- 未增加依赖，协议保持 10；消息帧合并/增量投影保持既有实现。

### 性能证据

同一环境、Chromium 无头、每组 20 字，时间包含 Playwright 发键与双帧等待：

| 场景 | 中位数 | P95 | 长任务 |
| --- | ---: | ---: | ---: |
| 优化前开发模式 251 行 | 151.1ms | 199.8ms | 20 |
| 优化后开发模式 250 条合成历史 | 约 50ms | 约 53ms | 0 |
| 优化后开发模式 1,000 条合成历史 | 约 117ms | 约 133ms | 0 |
| 优化后生产构建 250 条 | 33.2ms | 34.5ms | 0 |
| 优化后生产构建 1,000 条 | 33.2ms | 35.7ms | 0 |

开发模式计数通过测试浏览器响应注入组件入口计数器，未在生产组件加入诊断；输入和纯文本流式窗口内无关会话行执行为零，SSE 订阅数保持不变。当前会话自身的活动时间、运行状态更新允许刷新。Fiber 的 PerformedWork 标记在 bailout 后可能保留，因此不作为组件执行次数。

千条开发模式超过 250 条的建议时间预算，属于剩余边界；生产对照未出现同等增长，当前无需引入虚拟列表。长聊天 Markdown、超长会话树和布局初次挂载不在本轮性能结论内。
