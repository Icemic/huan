## 1. 主线与判断标准

产品目标是完整封装Pi基础GUI，供日常使用和huan自迭代。当前阻塞工作是整体架构整改：统一前端业务状态为Zustand、移除aui平行状态、明确前后端所有权和资源生命周期、修复已登记遗漏，并完成展示、测试与文档整理。

R2为这些改动确定必要的接口行为。每个新增机制必须能指出对应的能力要求或已确认缺陷，并说明现有状态同步、准入或领域接口为何不足。源码存在边界只形成研究依据，不能直接推出新产品流程。

## 3. 创建、发送与网络失败

### 3.1 提交输入与首次发送

R1的本地提交ID只在windowStore区分本窗异步动作，用于草稿清理、输入历史和取消准备；不承担服务端队列身份或跨刷新审计。

应用业务动作在开始时一次捕获目标、模型/Thinking、文字、附件和draftRevision。新会话统一走创建→取得threadId→发送的动作路径，显式传创建输入，删除HTTP包装偷偷读模型草稿及aui初始化分支。`initialMessage`随旧的重复创建/发送入口删除；这项调整用于明确唯一业务入口，与回执登记系统无关。

图片准备和能力预检在创建前进行，服务端发送前仍校验。创建成功后发送被拒，保留已创建会话及输入；已取得的threadId不因后续发送失败而丢失。目录合并服务端已创建的live会话，空会话文件尚未生成时也能在当前服务中找到；不承诺尚未保存的空会话跨服务重启存在。

### 3.2 请求结果

| 收到的结果 | 客户端处理 |
| --- | --- |
| started | 输入已接受，运行继续；不等待模型完成才返回 |
| queued | 输入已进入服务端队列；后续队列以SSE/快照为准 |
| handled | SDK扩展/input已处理；结束本次提交提示，不等待并不存在的聊天消息 |
| cancelled或明确的业务拒绝 | 结束对应提交，保留可恢复输入；不结束其他运行 |
| 网络断开/请求失败，无法确认结果 | 提示尚未确认，重新同步会话/队列/目录；保留输入供用户查看，绝不自行重新发送 |

这些是现有disposition的明确使用方式，不新增通用OperationState、结果表或查询端点。普通业务错误沿用现有类型和状态码，客户端不能仅由HTTP 4xx/5xx推断扩展外部操作是否执行过。

当前代码没有自动重投发送的行为；此前讨论中的重复执行只是错误处理应避免的方式，不能描述为已发生缺陷。同步只能恢复服务端已有状态；无法从服务端读取的任意命令副作用不由Harness推测或补建记录。

### 3.3 草稿与历史

只对捕获的draftId/revision清理输入；同目标新输入、切走返回后的输入和新附件保留。已接受的本窗动作登记一次输入历史，包含handled；其他窗口消息或历史加载不补记。网络结果未知时不从同文消息猜测已接受，不补写历史；用户仍能在当前窗口找到原输入。

创建失败先重扫目录，已知创建成功则直接保留对应ID。重新连接仅同步，用户明确再次发送/新建属于新的操作。界面不提供无依据的“安全重试”承诺，也不建设跨重启的提交恢复系统。

## 4. 服务端并发与队列

### 4.1 统一准入，按操作选择互斥规则

所有共享变更由服务端检查并提交。每会话的发送预检准入、结构闸门、取消资格继续由R1的coordinator唯一管理；检查与占用在第一个await前完成。浏览器busy只改善交互，不能代替服务端准入。

| 操作 | 服务端规则 | 客户端冲突处理 |
| --- | --- | --- |
| 普通发送/steer/follow-up | 沿用现有多窗口接受与SDK排队语义；准入顺序由服务端决定 | 展示服务端结果；窗口自身不派发同一在途动作两次 |
| 树导航/fork/标签 | 结构闸门及已有expectedTreeRevision校验 | busy/conflict后重读，保留草稿与用户选择 |
| 设置/MCP配置/工作区修改 | 现有revision及串行保存 | 冲突保留未保存输入，用户重读处理 |
| MCP运行管理/认证 | 现有runtimeId/identity与领域互斥 | stale/busy后同步对应安全状态 |
| 停止/整体取回 | 服务端捕获本次作用的当前运行/队列/在途集合 | 旧请求完成只更新原目标，不能清后来新队列或新草稿 |

用户提出的“两个窗口带同一版本，后到者拒绝”适合依赖旧状态的更新，已有树/配置revision应保留。是否将该规则扩展到普通追加消息，是行为变更；此前讨论尚未确认，当前方案保持既有多窗口发送能力，不暗加全局版本冲突。需要特定互斥时在对应服务动作实现，不给全部请求增加统一controlRevision。

### 4.2 服务端队列是唯一展示来源

前端已确认队列直接使用服务端快照/queue_update中的steering和followUp。本窗正在准备或等待HTTP返回的提交是独立本地提示，不插入另一份可写队列；接受后结束本地提交提示。A/B窗口同文发送均显示服务端结果；删除按文本出现次数认领、消费和合并的逻辑。

SDK只有整体clearQueue，沿用该能力。整体取回返回服务端取出的文本；本窗尚未派发的内容可在本地直接取消并恢复。两者不按文字去重。派发结果尚不明确的内容保留为单独提示，不能混入取回文本并冒充服务器认定。

取回响应不直接将当前队列设空；使用相应服务端事件或重查确认，以免迟到HTTP覆盖后来入队。草稿版本已改变时保留取回内容入口，不覆盖新输入。SDK未提供的逐项删除、来源识别或附件取回不由客户端伪造。

## 5. 运行结算与取消

agent_end表示一段agent执行结束，后续仍可能重试、压缩或继续。界面保持运行到agent_settled或权威快照确认结算；retry/compaction状态沿用现有字段，通过selector组合展示，不新增多阶段通用run状态机。

| 场景 | 必须保持的行为 |
| --- | --- |
| 接受/运行结束 | 接受与执行完成分开；agent_end不提前idle；最终失败/取消由服务端裁定 |
| 预检取消或handled | 只结束该提交；取消提示不能用作另一运行的结束信号 |
| 停止 | 覆盖当前预检、运行、自动继续与未交付队列，解除阻断UI；保持正常同会话继续能力 |
| Shell/手动结构操作 | 使用既有独立取消入口；Shell取消不停止模型运行 |
| 断开/关闭页面 | 只释放浏览器资源，Node任务继续 |

保留现有发送归属、取消租约、admission与结构互斥行为；重构不把这些控制散回各面板。必要SDK私有补偿集中，能力变化须有明确诊断及对应测试，不能静默失效；不因字段检测失败就给所有会话新建不可执行模式。

已知退休后延迟动作拦截有既有测试，必须保留。waitForIdle不能单独证明外层局部批次结束，但“停止→新提交→旧局部动作恢复”尚未运行证明为当前缺陷。继续在AR-21核对现有守卫与所需证据；只有确认不足时才设计针对性修正，新增私有耦合需另行说明；本方案不安排私有方法包装、批次跟踪或停止重建。

## 6. 快照、版本与错误

### 6.1 权威快照与本地请求代次

保持HTTP只读查询与SSE增量。每次新建/恢复订阅取得同一序号边界的完整快照，再接后续事件；最终browser只使用这条恢复路径。threadId仍为会话身份，seq仍为事件水位；stream/request epoch用于本地拒绝旧回调，不新增wire身份层。

完整快照按约定覆盖所属会话字段：缺省数组为空，缺省可选值为未知/不存在，contextUsage/readiness等不能用旧值填补。队列、交互与瞬态状态以本次快照为准；冷快照仅表达可读历史，不执行扩展。HTTP读取开始后若已有新事件，迟到读取不得覆盖新状态；新订阅首帧允许重置旧序号。

运行中重连须能显示当前可取得的消息、待答请求和工具状态。优先复用SDK公开state及服务端已维护状态；确实缺少的活动工具恢复投影按AR-37补必要字段，不建立第二份执行记录。完整快照的来源entryId、当前消息与工具字段若不足以恢复已登记行为，先给出确定的缺失例子，再补对应的最小字段；这一原则不排除必要修复，也不以保留现有wire为兼容目标。

### 6.2 目录与查询

服务端列表与live事件更新同一元数据实体。扫描/查询带本地请求代次，事件更新后旧读取失效；列表只覆盖其负责的目录字段，不清掉会话运行数据。创建/改名/归档/删除等动作显式更新或失效目录，不依赖DOM通知。无需为每组字段实现通用版本合并引擎。

模型/命令目录按目标和现有resource/auth/modelCatalog版本失效。换目标立即使用新目标查询状态，失败不能让前目标目录参与图片能力判断。树、资源原文和详情按需读取；跨窗工作区定义继续使用显式/聚焦刷新。

### 6.3 协议版本与接口边界

同一仓库的浏览器和Node按同版部署。协议15作为本次破坏性接口调整的目标版本，实施首次修改wire时递增，当前常量仍为14。HostInfo提供protocolVersion，浏览器启动时比较，不符显示更新提示并停止继续业务初始化。采用一次明确比较，不建立范围协商、每请求多层身份头或旧版兼容。

HarnessClient按R1划分少量领域接口再组合，方法保持显式。可复用wire守卫归protocol，HTTP负责解析/Content-Type/体积限制，core负责路径作用域/信任/版本/准入；避免重复维护同一字段知识。服务端Host/Origin/token校验先于正文读取，既有安全限制继续保持。

错误沿用领域result联合与必要的`code/message`。网络/解码/连接错误与业务失败分别呈现；受保护内容采用受控文案。部分成功保留现有领域事实，例如文件已写而归属保存失败、会话设置已生效而默认保存失败。删除通用effects/recovery矩阵，不要求Harness证明任意命令副作用。

### 6.4 JSON-safe的最小处理

AR-20仍需关闭：扩展unknown载荷中的循环引用或BigInt不能使整个事件编码失败。core在现有映射/快照输出处共用一次JSON转换边界：BigInt用十进制字符串，非有限数字/数组中的undefined按JSON规则为null，对象中的undefined/function/symbol按JSON规则省略；当前祖先循环或无法编码的子载荷用可读“不支持的扩展数据”标记。

转换只处理需要展示的扩展数据，不改SDK执行参数、Pi历史或已知协议ID；普通共享引用不能误当循环。访问/编码抛错在该边界处理，不建立任意JS对象的保真序列化协议、特殊类型解码器或逐字段诊断体系。已知消息/正文与交互仍保留，出现回退有受控提示。秘密仍由认证/配置领域投影隔离，JSON处理不承担秘密识别。

保留已有SSE解码限额、慢客户端断开、导入/配置/认证大小限制，不引入无依据的新数值。长Markdown/树/首次布局仍归AR-32的代表性负载验证；发现具体传输限制再在同一问题下处理，不把分帧方案当整改前提，不能以截断内容冒充成功加载。

## 7. 交互、展示与管理的必要调整

| 已登记问题 | 最小要求 |
| --- | --- |
| AR-12/40迟到结果 | 固定thread/草稿/窗口选择/面板代次；旧结果可更新原对象事实，但不能改后来视图或输入 |
| AR-39 editor预填 | 保持confirm/select/input/editor原始类型，工具与游离路径保留prefill、多行和每请求答案状态 |
| AR-37/38及AR-14 | 读取已有parentToolCallId/nestedCalls，展示SDK已有历史摘要/不完整信息；图片按内容渲染，未知data可读回退 |
