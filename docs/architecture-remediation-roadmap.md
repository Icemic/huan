# 整体架构整改子路线图

日期：2026-11-02。分支：`refactor`。审查基线：`5ff6565`；业务代码与 `5400b8f` 一致。

本文由[主路线图 §2.5](roadmap.md#25-整体架构整改阻塞子路线图)授权维护整改范围、问题生命周期、步骤、依赖和解除阻塞条件。主路线图仅维护总阻塞与恢复决定，不复制本文的进度。具体方案和执行证据放入迭代文档。

## 1. 目标、范围与工作约定

### 1.1 总目标

整理前后端架构、状态所有权、业务流程、协议、生命周期、展示接入、测试与文档，关闭本次审查发现及整改过程中新增的全部问题，再恢复原路线图。前端业务状态统一使用 Zustand，彻底移除 assistant-ui 状态体系与包依赖；这两项属于整体整改，不能单独代表整改完成。

原 G1.1～G1.4 的交付记录保留；发现的验收遗漏在本文重开。G1.5、原聊天展示升级 V0～V3 及其他新增功能暂停。文件快照、IDE 工作台、桌面分发和末语工坊接入继续延后，不借整改提前建设。

### 1.2 已确认的实施约束

- `refactor` 是允许内部破坏的工作分支。中间提交可无法启动、构建失败或测试失败，提交说明标明 WIP 和已知断点；合并前才要求完整可用。步骤交付不等于能力验收。
- 直接实现最终结构，不为中间检查通过建设兼容接口、双状态同步、双运行时、功能开关或一次性 adapter。不把既有测试数量、旧 API、DOM 或文件名当兼容目标。
- 前端业务状态的存储、动作与订阅统一采用 Zustand，包含现有 Controller、aui、Context 和分散 store 承担的业务状态。纯 reducer、投影与算法可以复用；不能保留 Controller 私有状态/listeners，再向 Zustand 复制一份。Context 仅可传递实例与依赖。
- React/Base UI 的组件内部交互机制、DOM ref，以及 transport 的连接/AbortController/定时器等资源，不作为另一套业务 store；其生命周期仍须明确。不得用此边界继续隐藏业务状态或恢复模块单例 store。Node 的 Pi/服务端权威状态保持服务端职责，不复制到浏览器作为新权威。
- 主 agent 负责设计、取舍、独立 review 和最终验证。方案确认与实施授权后才委派编码；worker 使用 `local/deepseek-v4.1-flash`，预检 provider/model 并记录 reasoning。不委派 review，默认不 push。

当前已授权文档、启动调研与R0能力/历史验收盘点，不修改生产代码、依赖或测试，不运行探针和业务验证。后续实施授权另行确认。

### 1.3 问题关闭规则

问题分为架构问题（A）、行为缺陷（B）、文档/验收不符（D）、待核实疑点（Q）。证据标为源码/历史确认、既有运行证据或待验证。严重度高/中/低只决定排序，不决定是否可以遗漏。

状态使用：待设计、待核实、实施中、待最终验证、已关闭。关闭必须关联最终实现、规范和验证证据；纯文档问题须关联纠正文档。疑点经研究证明不是问题时记录理由与证据。拆分/合并保留原 ID 和映射，不删除问题隐瞒进度，延期或豁免须经用户明确决定。

问题清单初稿与R0逐项盘点分别记录审查发现和能力证据。R0覆盖全部稳定能力ID及工作区、主题、性能等已交付要求，证据见[能力盘点](iteration/2026-11/2026-11-02-test-architecture-remediation-inventory.md)。源码阅读和既有测试仍有验证边界，后续发现立即补稳定 ID，并安排在本次阻塞内处理。所有记录均关闭后才允许解除阻塞。

## 5. 如何开始

启动研究见[所有权与启动设计](iteration/2026-11/2026-11-02-feat-architecture-remediation-start.md)。该文档给出已核对的职责分布、建议模型与待决定细节，实施须另行授权。

第一份设计交付应同时覆盖：

1. 状态与资源所有权表：服务端、窗口、会话、面板、派生视图与连接资源，不遗漏设置/MCP草稿和认证状态。
2. 完整业务时序：首次创建/提交、已有会话提交/排队/停止、树/fork/import、配置/认证/重载与销毁；明确同目标新输入和切换后的晚响应。
3. 最终模块图与迁移清单：每个旧状态/资源/公开入口的唯一去向，哪些算法保留、哪些旧抽象删除。
4. 规范与测试对照：每项已交付能力、AR问题和最终证据需求关联；不在调研阶段写临时测试。
5. 需要用户决定的少量设计问题：主agent先给源码依据和推荐，再讨论，不把已确定的Zustand/去aui/整体范围重新开放。

首个编码工作包在以上设计确认后确定。禁止把“先建一个Zustand store并同步旧Controller”当第一步。

## 6. 最终验证与解除阻塞

### 6.1 功能与安全

G1已交付适用能力逐项重新对照[能力规范](pi-gui-capabilities.md)，并修复本清单遗漏；未交付OUT功能不借整改计为完成。保留默认/自定义用户空间、信任、冷历史只读、多窗口、断线快照恢复、预检取消、队列与结构操作、扩展交互、配置保存≠应用、认证与MCP唯一连接/子孙回收。

自动化仅使用临时用户空间、合成模型、本地stdio/HTTP/OAuth fixture；不读取个人凭据/会话或开发助手MCP配置，不请求付费模型。不停止用户8799/8788服务；浏览器8899/8898单worker顺序执行。

### 6.2 工程与证据

- 最终执行check、build、Lingui与相关完整浏览器回归；正确的既有行为保持，错误断言按新规范改正，旧实现绑定测试迁移。逐项保持/补齐有意义的证据，不以983/69数字为目标。
- 检查包依赖方向、唯一Zustand状态来源、导出、无兼容残留、无重复发送/双滚动；保留必要的纯算法与MIT来源。
- 性能覆盖既有250/1000会话无关行与连接数约束，补经研究确定的长输出/树/首次布局指标。测量方法如实记录，不把Playwright往返当INP。
- UI交互、DOM/溢出与视觉判断分开记录；没有实际看过产物不能声明视觉通过。手工平台检查按项目规则记录，不能据此跳过已发现而未修复的问题。
- 偶发失败不静默重试到绿；记录首次失败、原因和修复/复查证据，环境问题分类有依据。
